# Designing changes in Forge

For changes that span guest functions, transformations, or output targets, see the [program architecture review](program-architecture.md). It traces a direct-call lift and documents the lifetimes of source facts, proofs and executable state.

## Component responsibilities

The CLI owns command registration, argument parsing, reports, diagnostic formatting and exit codes. Its executors call the compiler library. Future commands for native compilation, packaging, Blueprints and runtime configuration belong here. The CLI may coordinate runtime packaging or execution without linking a runtime implementation.

### Compiler and runtime

The compiler owns PE input and metadata, function and program recovery, and analysis of registers, flags, and guest addresses. Its `forge_core` library owns the diagnostic model and provides APIs to generate, verify, and publish LLVM IR. The stack checks and image-memory operations that Forge emits into a module are part of code generation. The library builds independently of CLI11 and the runtime.

The differential harness runs LLVM’s `opt` on the generated module to test the O2 variant. Future production transformations belong in the compiler. [Differential build rules](../tests/CMakeLists.txt)

For a runtime change, start with the resource owner, its borrowers and the guest-visible result. Compiler proofs and guest call lowering belong in the compiler. Runtime state and service behavior belong behind the versioned C ABI. The runtime architecture defines these contracts for both function entries and managed process artifacts. [Component boundaries](runtime-architecture.md#runtime-component-boundaries) · [Resource ownership](runtime-architecture.md#resource-ownership-and-borrowing)

### Adding a runtime service

Start in `runtime/src/compat/win32/` for Win32 services and `runtime/src/compat/crt/` for MSVCRT services. Use the ownership matrix to find the module that implements the relevant behavior. Extend it when the new operation shares its state, lifetime and failure rules. A new component earns its place when it isolates a real dependency, owns a distinct resource or serves multiple existing callers, as the shared checked string scan does. An export from another DLL can delegate to the same adapter. If that adapter needs process resources, also test that registration prepares them for the new export. [Source ownership matrix](runtime-architecture.md#runtime-source-ownership)

| Change | Where to put it and what to check |
| --- | --- |
| Win32 API | Put observable behavior in Win32. For `SetUnhandledExceptionFilter`, exchange an opaque guest VA on the active process, return the previous value and preserve last error. Keep fault reporting in core. Casting that VA to a native function pointer would bypass guest call validation. |
| CRT function | Put CRT return values, errno and startup data with MSVCRT or the relevant CRT implementation. A `calloc` overflow produces a null guest result and CRT errno. Use the process's allocation and registration path so freed memory becomes inaccessible through every guest access path. |
| Guest-memory feature | Put range publication, permission checks, stack protection and faults in core. Use the existing checked operations for a service buffer. A second address map in a service could accept a stale mapping after free or detach. Put a proof that permits a direct translated load in the compiler. |
| Host operation | Put native descriptor, timing and VM operations behind a narrow Darwin interface. For standard output the native operation reports bytes transferred and the host error. Win32 `WriteFile` validates guest buffers, commits the count and maps the outcome to a Windows result. The owning host controls signal policy. |

Declare the native C adapter and use one binding in the shared catalogue for the export, guest signature, pointer direction and extent, error policy, process requirement and control flow. Reuse that binding in lowering and typed service buffers. Keep a terminal guest result inside the process ABI so the embedding host regains control. [Import path and catalogue](runtime-architecture.md#from-pe-import-to-native-call)

Test the smallest observable contract first. Runtime unit tests can assert return bits, last error or errno, process isolation, invalid invocations, guest faults and the order of side effects. For a pointer or handle service include an invalid buffer or partial transfer where applicable. Use a lifted import fixture to exercise the actual guest argument positions and result propagation. Use a managed executable when registration, exit or startup is part of the behavior. Compare defined exit status, output bytes and other relevant effects with a pinned reference, recording which stages ran. [Runtime process tests](../tests/unit/runtime_process.cpp) · [Write tests](../tests/unit/runtime_write.cpp) · [Lifted ABI tests](../tests/integration/test_service_abi.py) · [Executable comparison](../tests/differential/fixtures/startup/README.md)

## Where does the change belong?

The CLI calls `forge_core`. Inspection follows imports across files and returns a report. Analysis and lifting share one parsed image. The CLI can render the analysis or request a verified LLVM module and pass it to publication. Keep dependencies pointing toward the data each stage consumes. Core contract tests call these same interfaces directly.

| Component | Responsibility and contract |
| --- | --- |
| [File input](../compiler/src/pe/input.h) | `InputFile` owns the open descriptor. Validation, physical file identity, and the byte snapshot come from that descriptor. |
| [PE parsing](../compiler/src/pe/image.h) | `ParsedImage` owns the snapshot, the LLVM COFF object that borrows it, and the observed PE metadata in `forge::Module`. Put file-format facts and checked RVA mapping here. |
| [Dependency inspection](../compiler/src/pe/dependencies.h) | `inspect` uses `inspectPE` to obtain detached module metadata. It resolves imports in the importing directory and configured search paths, then returns modules, locations, and dependency edges in a `Report`. DLL search policy belongs here. |
| [Function analysis](../compiler/src/analysis/analysis.h) | `AnalyzedImage` owns its `ParsedImage`. It derives function ranges, overlaps, findings, and eligibility from the parsed records. Optional debug enrichment uses the same image. |
| [Lifting](../compiler/src/lift/lift.h) | `generateIR` validates the request against the borrowed analysis. The [recovered group](../compiler/src/lift/recovery.h) owns the reachable CFGs and validated calls. [Group analysis](../compiler/src/lift/group_analysis.h) prepares the proofs and memory plan for the selected entry contract and guest base. LLVM emission uses these inputs to build and verify the caller-owned module. |
| [Publication](../compiler/src/output/publication.h) | `publishIR` borrows the completed module and parsed image. It checks the requested destination and owns the file operations that replace it. The [native output stage](../compiler/src/output/executable.h) also emits ARM64 objects and links verified macOS executables with the configured toolchain. |
| [CLI](../cli/src/main.cpp) | The entry point registers commands and handles help and usage errors. Each command selects policies, sequences core calls, and returns an exit status. Renderers consume reports, findings, and classified errors. |

## Adding a CLI command

1. Follow the [inspect implementation](../cli/src/commands/inspect.cpp). Put the option struct and registration declaration in a header under `cli/src/commands/`. Store paths, flags, and existing core request types by value. Keep command-specific options, validation, and help text in the matching implementation.
2. In `main.cpp`, declare the options before the `CLI::App`, then call the registration function with the app, options, and exit status. CLI11 retains references to option storage. Bind a `final_callback` that calls the typed executor and records its return value. It runs after help and argument checks. Use `trigger_on_parse()` for options whose every occurrence needs validation.
3. Keep the executor independent of CLI11. Call the owning core interfaces, render reports to stdout and diagnostics to stderr, and return the command's status. Use `parsing.h` for shared input and report options and `report.h` for existing renderers. Add the command's sources to the `forge` target in [the CLI build](../cli/CMakeLists.txt).
4. Exercise the public syntax, both streams, and exit status in the [CLI suite](../tests/integration/test_inspect.py). For a separately testable executor, see the [typed lift test](../tests/unit/lift_command.cpp), which calls the production executor with a generated PE fixture and a diagnostic stream. Register tests in `tests/CMakeLists.txt`.

From the repository root, run the focused tests with fixture setup, including when the build was previously configured with tests disabled.

```sh
make provision
make test CONFIG=Debug BUILD_TESTING=ON CTEST_ARGS='-R "^(cli|lift_command)$$"'
```

## Extending an existing component

1. Trace a similar change from a caller through the owning interface to a test. Identify the first stage with enough information to answer the new question. An import's spelling comes from parsing, its resolution status comes from inspection, and its displayed text comes from the CLI.
2. Use the owner's existing model, parser, validation, and error mechanism. List the input assumptions, output guarantees, failure classifications, and observable behavior callers rely on. If any must change, identify the affected callers and describe the revised contract.
3. Trace each borrowed value back to its owner. Both the section and bytes returned by `ParsedImage::mapRva` borrow the image. Pass the image down while those views are in use. Reopening its path could read a replacement file. Reuse the parsed image and make the borrow explicit before considering shared ownership. Follow the [C++ style guide](cpp-style.md) and its [ownership and borrowed storage rules](cpp-style.md#ownership-and-borrowed-storage).
4. Test the rule at the lowest level that can observe it. Add a contract or CLI test when data, errors, or side effects cross a boundary. For new lifting behavior, compare defined guest results against an independent reference. Preserve negative cases and enabled comparisons. An enabled case that starts returning “unsupported” is a regression. [Test layers](../AGENTS.md#test-layers) and [differential coverage rules](../tests/differential/README.md#regression-ci-and-local-reproduction)

## When to introduce a component

Extract a component when the change introduces a distinct responsibility or resource lifetime. For a new component or meaningful cross-stage change, a short note in the change description is enough. Small edits can follow the existing contract directly.

```text
Responsibility:
Why an existing component is not the right owner:
Inputs, outputs, and dependencies:
Ownership and lifetime:
Failure behavior and preserved invariants:
How the contract will be tested:
```

Use a **function** for an operation with no state to retain between calls. Use a **value type** for data that travels together, such as the start RVA and entry mode in `LiftRequest`. Use an **owning object** when resources must share a lifetime or destruction order, as the COFF object and its backing bytes do in `ParsedImage`. Introduce an **interface** when a current caller needs to use different implementations through the same contract. Use LLVM types directly where the contract already calls for decoded instructions or IR.

Keep helpers with the responsibility they serve. A long file or a new directory alone does not warrant a component or library. Speculative factories, backend registries, inheritance hierarchies, catch-all utilities, and generic managers make it harder to find the owner of a rule.

## Forge-specific decisions

- **Executable entry.** The compiler selects the header RVA and verifies its startup requirements against the reachable group. The native bootstrap owns the one-shot host lifecycle and maps the tagged result to an exit status. The process ABI owns image, thread, and stack initialization. [Standalone executable contract](../README.md#compile-and-run-a-native-executable)
- **Guest and output target.** PE machine metadata identifies the guest. AMD64 is the implemented guest, and the typed entry wrapper models Windows x64 calling semantics. The output module has its own ARM64 macOS triple and data layout. A future 32-bit x86 guest would need its own validated input, discovery, and calling semantics before a shared CPU abstraction could serve it. [Lifting interface and targets](../README.md#lifting-interface-and-targets)
- **Addresses.** A file offset indexes snapshot bytes. An RVA is relative to the image base. A guest virtual address, such as a TLS callback address, needs a checked conversion before comparison with an RVA. Use `mapRva` for file-backed bytes. A host pointer refers to storage in Forge's process and carries that storage's lifetime. Equal integer widths do not justify conversions between these quantities.
- **Invocation state.** The retained register-state adapter owns the execution context, copies the public slots at its boundary and initializes registers, opaque origins, flags and checked stack storage once. Each RVA-named guest body borrows that context. Call sites keep expected frame values in their LLVM activation and validate them when control returns. The stack validity array also marks each live nested return address. Copies of those bytes are concrete guest values. Guard continuations are the real predecessors of successor flag PHIs. [Guest stack memory](../README.md#guest-stack-memory)
- **Source recovery.** Add a callee recovery rule at the recovered-group boundary. The snapshot and explicit entry RVA identify every function. For an inferred leaf, the mapped window bounds decoding and the CFG steps own the instruction extents. Incoming indices borrow the caller’s resolved call-site records. Establish each target from decoded source evidence before group analysis. Record the producer RVA and use the decoded CALL operand for the runtime check. Validate the candidate before registering its CFG or constructing IR. Keep recorded ranges in PE analysis. [Leaf recovery policy](program-architecture.md#recovering-a-called-leaf-without-unwind-metadata)
- **Indirect branch proofs.** Keep the table evidence and index-ordered edges on the recovered guest block. Validate bounds against every edge in the finished graph before exposing it to analysis. Memory preparation consumes the proven load span, and emission uses the actual guest target address. Flag PHI multiplicity follows emitted edges when several table entries share a destination. [Bounded indirect branches](program-architecture.md#bounded-indirect-branches)
- **Call analysis.** Use the recovered site for the callee, the fallthrough RVA and incoming-call traversal. Attach derived effects to that site. Derive register writes and flag effects over each block in instruction order. Compute normal-return effects to a fixed point over the discovered functions, then propagate the actual entry definitions from all callers. Keep flag bits that a body can carry separate from flags proved available for consumption. A shared helper may preserve a defined caller flag even when another caller enters with it undefined. The address worklist propagates the four register arguments, possible entry RSPs, and RAX on normal returns. A missing call or return path is distinct from an unknown guest value. Invalidate other volatile facts and stack saves across calls since the callee may store through an alias. Keep a nested frame’s symbolic displacement separate from absolute VAs. A full-width read at that frame’s entry RSP identifies the callee’s set of continuation RVAs. Only dereferences with this provenance select exact executable byte ranges. Collect image spans after the address facts stabilize, then emit one module resolver.
- **Image initialization.** `ParsedImage` owns the file snapshot, section layout, and parsed relocation records. The COFF stripped-relocations flag determines whether the lifter must use the preferred base. The initialization view identifies supported data fixups and protected RVA intervals, including loader-written slots and conflicting fixups. Validate a direct access against its own byte range. A shared writable backing can contain protected bytes, which its resolver intervals exclude. A `DIR64` uses the complete loader-visible field, even for a narrow read or a field spanning the raw/zero boundary. Keep metadata-derived addresses relative to the preferred base. Apply the selected guest base when producing the field value, planning RIP-relative accesses, and emitting resolver intervals. [PE image mapping and limits](../README.md#pe-image-memory)
- **Image lifetime.** During preparation, `ImageMemory` merges immutable spans and selects writable sections by RVA. Its finished plan carries the relocated bytes and accessible intervals into emission. Function-level resolver intervals for a writable section reference the same module-owned global. Fully initialized sections can carry a static LLVM initializer. Mixed sections use contiguous zero-backed storage. Ordinary entries and the module constructor share an idempotent initializer for the prefix and relocated tail bytes. Checked entries finish synchronized initialization in the descriptor accessor before publishing the intervals. Mark this backing `externally_initialized` to keep LLVM's global optimizer from materializing the entire tail. After initialization, entry calls reuse that storage. A process artifact carries the same initialization plan as immutable backing templates and sparse relocation fragments. Registration materializes them in each process and the generated resolver borrows that process’s bound table.
- **Selecting an access.** The CFG worklist tracks bounded sets of exact guest values in registers and full-width stack saves. Copying a block state shares its spill map. A write or join detaches a shared map only when it changes a fact. A join unions possible values. An ordinary spill is known only when every incoming path establishes it. A path that saves a continuation can still select its code bytes when another path leaves the spill unknown. A later overlapping write invalidates the affected saves. Writes through numeric aliases invalidate overlapping saves. A write through an unknown address discards the state's spill map. Collect image spans after the worklist converges. Keep the proof for stack-only routing distinct from the integer values used for selection. Recovering a numeric offset from a zeroing idiom or 32-bit arithmetic must preserve runtime stack/image dispatch for an address that previously used it. [PE image memory](../README.md#pe-image-memory)
- **Translating an access.** Decode the MC base, index, scale and displacement into a 64-bit guest VA. Proven stack accesses and implicit stack operations use the checked invocation stack. Other memory operations dispatch by guest address. The image resolver binary-searches sorted, disjoint intervals by unsigned start VA. It checks the candidate's full width and permission before deriving a native pointer. Read-modify-write operands use the same integer semantics as register operands. Stack stores preserve per-byte origins, while image stores require concrete bytes. Keep the actual guard continuation as the predecessor supplied to flag PHIs. [Guest stack contract](../README.md#guest-stack-memory)
- **Saving incoming registers.** When a body can touch opaque nonvolatiles, its register slots carry per-byte origins alongside their bits. The stack uses its existing validity bytes for the same marks. Each incoming nonvolatile byte has a unique identity. LLVM `freeze` supplies a stable backing value for the invocation. Plain MOV and stack transfers copy bytes and marks together, including copies into volatile registers. A register-only save can introduce an opaque value even when the function never writes the source register. Computational consumers require concrete marks, while restoration checks both the captured bits and their original identities. Nested returns validate the actual incoming bits and origins for the activation. The outer typed entry also requires a concrete RAX. The signatureless outer entry requires concrete bytes in all seven exposed slots.
- **Facts and policy.** Keep the raw record, the analysis conclusion, and the caller's selection distinguishable. For example, `--signature` selects an entry mode. It supplies no evidence about the original function's type. `ParsePolicy::Inspection` reads import and export tables and rejects a partial exception record. `ParsePolicy::FunctionAnalysis` skips those tables, retains complete exception records, and lets analysis report trailing bytes as a finding. Preserve both contracts when extending their shared parser. [Image ownership and stage contracts](../README.md#image-ownership-and-stage-contracts)
- **Failures.** Assign an `InspectionError` its `FailureCode` where the cause is known. Carry owned context through callers. Malformed input, unsupported capabilities, I/O failures, and internal defects have distinct consequences for consumers. Classify lift failures by stage, category, and code. Parsing diagnostic prose makes a wording change alter program behavior. [Failure definitions](../compiler/src/diagnostics.def) and [CLI diagnostic schema](../README.md#lift-diagnostics)

## Worked examples

### Extending the lifter with an immediate multiply (hypothetical)

Forge supports register-pair `IMUL`. Suppose we wanted to lift `imul rdx, rcx, -3` (Intel syntax). LLVM decodes it as `IMUL64rri8`. Today `x86::integerInstruction` excludes immediate multiply. Merely accepting the suffix would send it through a path in `Translator::integer` that reads the old destination. With RCX = 4 and RDX = 7, that would give −21. The guest result is −12. [Form recognition](../compiler/src/lift/integer.cpp) and [operand lowering](../compiler/src/lift/lift.cpp)

The extension would read RCX and the signed immediate, reuse `IntegerSemantics::arithmetic` for the product and its carry and overflow flags, and write RDX. Instruction bytes would still borrow the analyzed image. A unit test could check form recognition, and a negative lift test should still get `LIFT_UNSUPPORTED_INSTRUCTION` for the neighboring memory form `IMUL64rmi8`. A differential fixture modeled on `multiply_flags` would use distinct register values and expose the product and defined flags. Compare baseline and optimized native runs with Wine for ordinary and overflowing inputs. [Integer unit tests](../tests/unit/integer.cpp) and [assembly fixtures](../tests/differential/fixtures/arithmetic/integer_cases.S)

### Why publication warrants a component (implemented)

`generateIR` returns a verified module that the caller owns. The image can be destroyed after generation. The caller's `LLVMContext` must outlive the module. Opening the destination inside the translator would let an unsupported instruction truncate an existing file and would impose filesystem effects on in-memory callers. [Generation and lifetime tests](../tests/unit/lift.cpp)

Publication has a separate resource lifetime. The CLI preflights the path with `checkedOutputDestination`. At publication, `publishIR` checks it again against the borrowed image's captured file identity and original directory entry. Publication owns a sibling temporary through writing and closing, then renames it into place. A write, close, or replacement failure carries a publication I/O code and triggers cleanup while preserving the previous destination. CLI tests exercise these guarantees by forcing a write failure and a failed replacement, checking both the old contents and the absence of a leftover temporary. [Publication implementation](../compiler/src/output/publication.cpp) and [CLI failure tests](../tests/integration/test_functions.py)
